IPv6 TCPing（检索时常写作 ipv6 tcping）用 TCP 握手验证 IPv6 地址与端口是否可达，比 Ping 更贴近真实业务流量。结果字段与 [IPv4 TCPing](/tcping) 相同（发送包、接收包、丢包率、最长/最短/平均时间），读法也一致。这一页只讲 IPv6 特有的失败链路。

## 能连通需要同时满足三件事

1. 域名有 **AAAA 记录**，且 DNS 能正常返回 IPv6 地址；
2. 服务端进程在 IPv6 地址上**监听**了目标端口（Nginx 需要 `listen [::]:443`）；
3. 防火墙、云安全组放行了源地址为 `::/0` 的该端口。

只做了第 1 步是最常见的情况：DNS 查得到、TCP 却连不上。

## 为什么要从多个节点做 IPv6 TCPing 测试

IPv6 的互联互通路径与 IPv4 并不重合，某个运营商到目标不通、另一个运营商却能通是常见现象。单节点测试只能说明「这条路径不通」，多节点并列结果才能区分是服务端没监听，还是中间链路没覆盖 IPv6。本页的每次检测都会从多个节点并发发起握手，方便直接按节点对比丢包率与 RTT。

## 按现象定位

| 现象 | 优先检查 |
| --- | --- |
| 解析 IP 为空 | AAAA 记录、DNS 是否支持 IPv6 查询 |
| IPv4 通、IPv6 全不通 | 服务端监听与安全组，基本可排除服务本身故障 |
| 部分节点通、部分不通 | 中间链路或运营商 IPv6 互联互通 |
| 本地就测不了 | 本机未获得 IPv6 地址，或网络优先级偏向 IPv4 |
